# 许可证：动手前先查，别等上架才发现

## 为什么这一步排在第 2 位

占卜类应用常被推荐使用的"现成命理算法包"，恰恰是许可证雷区最密集的地方。**写代码半小时，换许可证两周**——先查能省掉整个返工。

## 唯一的动作

```bash
npm view <包名> version license dependencies
```

三个字段各有用途：

- `license` —— 决定能不能闭源分发
- `dependencies` —— 决定离线打包体积，以及会不会间接拖进传染性许可证
- `version` —— 锁定版本，避免上游静默变更行为

Python 生态同理：`pip show <包名>` 看 License，或读包内 `METADATA`。

## 真实核查结果（2026 年实测，可供参考）

| 包 | 版本 | 许可证 | 依赖 | 能否闭源离线打包 |
|---|---|---|---|---|
| `lunar-javascript` | 1.7.7 | MIT | 零依赖 | 可以 |
| `iztro`（紫微斗数） | 2.6.3 | MIT | 本地小库 | 可以 |
| `mingyu-core` | 0.4.3 | **AGPL-3.0-only** | 若干 | **不可以（闭源场景）** |

> 版本号会变，**每次动手都要重新查**，不要照抄这张表。

## AGPL 到底意味着什么

GPL 的传染通常被理解为"修改了我的代码才要开源"，但 AGPL 更进一步：**通过网络向用户提供服务也算分发**。把 AGPL 库打进一个分发给用户的 App，实务上通常会导致：

- 整个 App 的源代码需要按 AGPL 提供；或
- 该库必须被彻底隔离为独立进程并满足其接口条款（工程成本极高，且法律判断需律师）

对一个打算闭源售卖的 App 来说，这是实质性障碍，不是"注意一下就行"的小事。

**结论：闭源商业 App 一律不引入 AGPL/GPL 依赖。**

## 安全路线

按能力从"直接可用"到"自己写"排：

1. **纯历法计算** → `lunar-javascript`（MIT、零依赖、UMD，浏览器 `<script>` 直接引）
2. **紫微斗数** → `iztro`（MIT）
3. **塔罗 / 六爻 / 牌阵 / 解读文案** → **自研**。牌义是静态数据，抽牌是随机数，牌阵是数据结构，规则解读是字符串组合。几百行就能写完，且完全自主可控。

第 3 条看起来"要自己写好多"，实际上比接入一个陌生 API 更快：不需要读别人文档、不需要处理网络失败、不需要担心版本升级破坏行为。

## 第三方远程服务同样要谨慎

即使不打包代码、只调用远程占卜 API（如各类命理 MCP 服务），仍有两件事要交代清楚：

- **数据出境**：用户的出生时间、感情/合作细节会发到对方服务器
- **服务可用性**：对方宕机，你的 App 就废了

面向消费者的正式产品，**本地算法优先**；远程服务只做实验或可选增强。

## 上线前自查

- 产物目录里没有 `node_modules` 里那些包的源码副本
- 没有引入 AGPL/GPL 包（`check_offline.py` 会扫 `package.json` 与 `node_modules/*/package.json`）
- 第三方库都已复制进 `vendor/` 并保留原始 LICENSE 文件
- App 内声明了所使用开源库的名称与许可证（MIT 也要求保留版权声明）
